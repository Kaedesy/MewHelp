# 高并发下单与交易一致性改造方案

## 1. 改造目标

本方案针对 Mall Swarm 现有的普通下单链路，解决并验证以下问题：

1. 多个请求同时购买同一 SKU 时，库存是否会超卖。
2. 客户端重试或重复点击时，是否会重复创建订单、重复占库存。
3. 支付成功与超时取消同时发生时，订单状态和库存操作是否一致。
4. 订单数据库事务与 RabbitMQ 消息发送之间发生故障时，业务流程是否能恢复。

目标不是简单地“加入 Redis”或“提升并发量”，而是建立可测试的业务不变量：

- 可售库存、锁定库存和实际库存不会出现负数。
- 对同一业务请求，最多创建一笔订单并占用一次库存。
- 一个订单只能从待支付状态成功迁移到已支付或已取消其中之一。
- 支付扣减库存、取消释放库存都只能生效一次。
- 订单成功创建后，超时取消事件最终可以被投递和处理；重复投递不会重复产生业务效果。

> 本文是改造设计和验证计划，不代表以下功能已经实现。每项完成后应以代码、自动化测试和压测结果为准。

## 2. 当前实现梳理

主要涉及的代码：

- 下单：`mall-portal/src/main/java/com/macro/mall/portal/service/impl/OmsPortalOrderServiceImpl.java`
- 订单服务接口与事务注解：`mall-portal/src/main/java/com/macro/mall/portal/service/OmsPortalOrderService.java`
- 库存及订单 SQL：`mall-portal/src/main/resources/dao/PortalOrderDao.xml`
- 延迟取消消息发送：`mall-portal/src/main/java/com/macro/mall/portal/component/CancelOrderSender.java`
- 延迟取消消息消费：`mall-portal/src/main/java/com/macro/mall/portal/component/CancelOrderReceiver.java`
- 数据库生成的 SKU Mapper：`mall-mbg/src/main/java/com/macro/mall/mapper/PmsSkuStockMapper.java`

### 2.1 下单与库存预占

`generateOrder()` 当前大致按以下顺序处理：

1. 根据当前会员和购物车读取商品、价格、促销信息。
2. 调用 `hasStock()` 检查购物项中的 `realStock`。
3. 计算优惠券、积分和订单金额。
4. 调用 `lockStock()`：逐个按 SKU 查询 `PmsSkuStock`，在 Java 中增加 `lockStock`，再调用 `updateByPrimaryKeySelective()` 写回。
5. 保存订单和订单项，更新优惠券、积分，删除已购买的购物车项目。
6. 发送 RabbitMQ 延迟消息，超时后尝试取消订单。

`generateOrder()` 在 `OmsPortalOrderService` 接口上声明了 `@Transactional`，其事务能否覆盖所有操作仍应通过集成测试确认，尤其要检查 Mapper、RabbitMQ 发送和异常回滚的实际边界。

### 2.2 支付与取消

- `paySuccess()` 将订单设置为已支付，然后调用 `PortalOrderDao.updateSkuStock()`：扣减 `stock` 和 `lock_stock`。
- `cancelOrder()` 先查询待支付订单，再将其设置为取消，随后释放锁定库存、恢复优惠券和积分。
- `CancelOrderReceiver` 收到超时消息后直接调用 `cancelOrder()`。
- `PortalOrderDao.xml` 中的支付库存更新按 SKU 批量更新，但 SQL 本身没有订单状态或库存锁定记录作为条件。
- `cancelOrder()` 的订单查询和后续更新分开执行；最终更新没有在 SQL 条件中再次限定 `status = 0`。

### 2.3 消息投递

订单保存流程会直接发送延迟取消消息。数据库事务和 RabbitMQ 发送是两个独立系统的操作，单靠 `@Transactional` 不能保证两边原子提交。

## 3. 已确认的问题与待验证风险

### 问题 A：库存检查和预占不是原子操作

`hasStock()` 检查购物车商品携带的库存值；之后 `lockStock()` 再次读取 SKU 并在 Java 中累加锁定库存。多笔请求可以同时通过前置检查，再基于相同旧值更新。

结果可能是锁定库存统计不准确，或并发下单超过可售库存。是否能稳定复现，应通过数据库并发测试确认；从实现结构看，检查与更新之间确实存在竞争窗口。

### 问题 B：重复提交没有明显的订单幂等键

下单接口如果被客户端重试，业务会重新读取购物车并走一次下单流程。当前已检查的下单链路没有体现“一个请求标识只允许创建一个订单”的幂等记录或唯一约束。

因此网络超时后的重试可能重复创建订单、扣积分/优惠券或占库存。应继续检查完整 Controller 和认证约束，但不能假定重复提交已被幂等保护。

### 问题 C：支付和取消的状态迁移不是条件原子迁移

取消流程先查询状态，再单独更新；支付流程也通过实体更新支付状态。两种操作可能并发读取到“待支付”，随后都继续执行库存处理。当前实现没有清楚地以“只有成功从待支付迁移的一方才执行库存副作用”作为统一门闩。

这属于需要用并发测试确认的竞态风险，而不是仅凭静态代码就断言每次都会造成错误。

### 问题 D：消息发送与数据库事务存在故障窗口

- 若订单事务提交成功，但进程在发送消息前退出，可能产生没有超时取消消息的订单。
- 若消息已发送，但订单数据库事务随后回滚，消费者可能收到没有对应有效订单的消息。

延迟消息消费者可以通过状态检查避免部分无效操作，但无法替代可靠投递机制。

## 4. 改造方案

### 4.1 将库存预占改为数据库原子条件更新

在 SKU 表上将“检查可用量 + 增加锁定量”放入同一条 SQL。建议使用明确的库存字段语义：

```sql
UPDATE pms_sku_stock
SET lock_stock = lock_stock + #{quantity}
WHERE id = #{skuId}
  AND stock - lock_stock >= #{quantity};
```

如果当前 `stock` 字段在支付时才扣减、锁定时不减少，则上述条件表达“可售库存 = stock - lock_stock”。必须先核对项目中 `stock`、`lock_stock` 和 `realStock` 的既有语义，再确定最终条件，避免字段含义不一致导致重复扣减。

处理规则：

1. 更新行数为 `1`：该 SKU 预占成功。
2. 更新行数为 `0`：库存不足或 SKU 不存在，抛出业务异常。
3. 一个订单有多个 SKU 时，所有预占都在下单数据库事务中执行；任一失败则回滚整笔订单及已成功的预占。
4. 对购物项按 SKU ID 排序后逐项更新，降低多 SKU 订单之间锁顺序相反造成死锁的概率。
5. 为 SKU 扣减 SQL 增加非负约束条件，并检查受影响行数；不能只依赖应用层预检查。

不建议第一步就把普通订单库存迁到 Redis。数据库原子条件更新是较小且可证明的改造；只有压测确认数据库热点行成为瓶颈后，再评估 Redis 预占、活动库存分片或排队方案，并补齐 Redis 与数据库间的补偿一致性。

### 4.2 增加下单请求幂等

客户端为一次下单生成 `Idempotency-Key`，服务端以“会员 ID + 幂等键”作为唯一业务键。

建议新增订单请求记录表，至少保存：

- `member_id`
- `idempotency_key`
- `request_hash`（购物项、地址、优惠等关键请求内容的摘要）
- `order_id` 或订单结果
- `status`（处理中、成功、失败）
- 创建和更新时间

实现要求：

1. `(member_id, idempotency_key)` 建唯一索引，使用数据库唯一约束作为并发兜底，不能只做 Redis `GET` 后 `SET`。
2. 首次请求创建幂等记录并执行下单；同键同请求重试，返回原订单结果。
3. 同键但请求内容不同，返回冲突错误，不能把旧键绑定到不同订单。
4. 幂等记录、订单、订单项和库存预占应处在一致的本地事务边界。
5. 对于处理中的重复请求，返回处理中或查询原请求状态，避免第二个请求重复执行副作用。

### 4.3 使用条件状态迁移协调支付与取消

将状态变更改为数据库条件更新，订单状态是并发竞争的唯一门闩：

```sql
UPDATE oms_order
SET status = #{targetStatus}, update_time = NOW()
WHERE id = #{orderId}
  AND status = #{expectedStatus}
  AND delete_status = 0;
```

处理规则：

- 支付：仅允许 `待支付 -> 已支付`；受影响行数为 `1` 的事务才能确认库存并登记支付结果。
- 取消：仅允许 `待支付 -> 已取消`；受影响行数为 `1` 的事务才能释放库存并返还优惠券/积分。
- 受影响行数为 `0`：说明订单已被另一条路径处理；查询当前状态并按幂等成功返回或报告冲突，不再重复处理库存。
- 订单状态和本地库存变更必须处在同一数据库事务中。
- 支付、取消及消费者重试都要覆盖重复调用场景。

需要重点核实库存释放 SQL：现在它仅按 SKU 和数量减少 `lock_stock`，没有绑定订单级预占记录。如果同时存在多个订单购买同一 SKU，必须确保某个订单释放的是自己的预占，而不是只按数量修改共享计数。可增加订单/SKU 维度库存预占记录，状态限定为 `LOCKED / CONFIRMED / RELEASED`，并用条件更新保证一次性迁移。

### 4.4 使用 Outbox 保证订单事件最终投递

在创建订单的同一个数据库事务中写入 `outbox_event`，记录事件 ID、事件类型、订单 ID、载荷、状态、重试次数和下次重试时间。后台发布器扫描待发送事件并发送 RabbitMQ；确认发送成功后标记完成。

关键要求：

1. 订单和 Outbox 记录同事务提交，因此订单提交成功就有可恢复的事件记录。
2. 发布器允许至少一次投递；消费者必须按事件 ID 或业务键幂等，不承诺消息系统与数据库之间的 exactly-once。
3. 处理并发发布时使用行锁/租约或原子认领，避免多个发布器长期重复处理同一批事件。
4. 失败事件采用有上限的退避重试；超过阈值进入死信/人工处理状态并告警。
5. 订单超时取消可以由事件调度器发布延迟消息；消费者仍需通过条件状态迁移决定是否真的取消。
6. 定时扫描待取消订单可以作为补偿任务，但必须与消息消费共享同一套幂等状态迁移逻辑。

## 5. 验证方案

### 5.1 自动化并发测试

测试使用 MySQL（不要仅用 H2/SQLite 替代），真实验证条件更新、事务和行锁行为。每个测试使用独立数据，避免互相污染。

#### 测试一：同 SKU 超卖验证

- SKU 可售库存设为 `100`。
- 并发发起至少 `500` 个购买 `1` 件的下单请求。
- 断言成功订单数 `<= 100`，失败请求返回库存不足。
- 断言数据库 `stock >= 0`、`lock_stock >= 0`，且库存预占明细与订单项数量一致。
- 重复多轮并发执行，检查是否存在偶发负库存或多占库存。

#### 测试二：多 SKU 部分预占失败回滚

- 订单包含 SKU-A 和 SKU-B；SKU-A 有库存，SKU-B 库存不足。
- 发起下单并断言失败。
- 断言订单、订单项、幂等成功结果均未持久化；SKU-A 的锁定库存恢复到请求前数值；优惠券、积分、购物车状态没有部分提交。

#### 测试三：同一幂等键并发重试

- 对同一会员、相同幂等键并发提交同一订单请求。
- 断言只生成一个订单、一次库存预占和一条有效超时事件。
- 相同幂等键但不同请求摘要时，断言返回冲突，不生成第二个订单。

#### 测试四：支付与取消并发竞争

- 准备一笔待支付且已锁库存的订单。
- 两个线程通过屏障同时触发支付成功与超时取消。
- 断言只有一个条件状态迁移成功；最终订单状态与库存状态匹配；重复执行支付或取消不改变最终库存。

#### 测试五：重复、失败消息和服务重启

- 对同一订单重复投递取消事件及支付事件。
- 模拟 RabbitMQ 不可用、Outbox 发布后进程退出、消费者处理前后重启。
- 断言 Outbox 未完成事件可重试；消费者重复执行不重复释放/扣减库存；终态事件可观测并触发告警。

### 5.2 压测与性能记录

使用 JMeter、Gatling 或 k6 对下单接口逐步增加并发，不要只记录最大 QPS：

- 固定环境、数据库配置、SKU 库存、商品数和请求分布。
- 记录吞吐量（RPS/QPS）、P50/P95/P99 延迟、错误率、成功/售罄比例。
- 同时采集 MySQL CPU、连接池使用率、锁等待/死锁、慢 SQL；RabbitMQ 队列深度、消费者速率和重试数。
- 分别测试普通 SKU 与单个热点 SKU，识别热点行锁和下游瓶颈。
- 改造前后使用同一环境和同一压测模型比较；记录原始报告，不编造目标或提升百分比。

### 5.3 一致性对账

增加只读对账脚本或管理查询，按 SKU 检查：

```text
库存表 lock_stock
与状态为 LOCKED 的订单级预占明细数量之和是否一致
```

按订单检查：

- 已支付订单应只有已确认的预占记录。
- 已取消订单不应保留有效锁定记录。
- 处理中 Outbox 事件超过阈值应可查询、告警和重放。

对账只用于发现与修复异常，不能替代下单主流程的原子性和幂等控制。任何自动修复都要记录修复前后值及原因。

## 6. 实施顺序

1. **先补测试与基线**：确认字段语义、事务边界，写出当前行为的并发复现测试。
2. **原子库存预占**：修改库存 SQL 和下单事务，先通过超卖及回滚测试。
3. **条件状态迁移与订单级库存预占记录**：解决支付/取消竞争和重复库存副作用。
4. **下单幂等**：增加幂等记录、唯一约束与重试行为。
5. **Outbox 可靠事件**：处理数据库与 RabbitMQ 的故障窗口。
6. **故障注入、压测、对账**：记录性能、正确性和恢复结果，再决定是否还需要 Redis 热点库存等更复杂方案。

## 7. 简历项目描述（改造完成后使用）

以下内容是基于本方案的目标简历稿，只有对应代码、测试和压测完成后才能作为已交付成果使用。未完成的条目应删除或改写为实际完成的范围。

### 项目名称

Mall Swarm 微服务商城——高并发下单与交易一致性改造

### 项目背景

基于 Mall Swarm 电商微服务项目，对下单与交易链路进行并发可靠性改造。原有流程采用应用层库存查询与更新，缺少明确的请求幂等机制；支付回调与超时取消存在并发状态竞争，订单数据库事务与 RabbitMQ 消息发送也无法保证原子性。在并发请求、客户端重试及服务异常场景下，可能出现超卖、重复下单、订单状态与库存不一致、超时事件遗漏等问题。改造聚焦库存正确性、订单状态互斥、支付异常补偿及消息可靠投递。

### 技术栈

Java 17、Spring Boot、Spring Cloud、MyBatis、MySQL、Redis、RabbitMQ、JUnit、JMeter（按实际使用的技术和工具填写）。

### 技术亮点

1. **数据库原子库存预占，防止并发超卖**  
   针对原实现先查询库存、再更新锁定量导致的竞争窗口，将可售库存判断和库存预占合并为带条件的原子 SQL，通过受影响行数判断预占结果；多 SKU 订单在同一数据库事务中统一预占，任一 SKU 失败则回滚整笔订单，并按 SKU ID 顺序执行更新以降低死锁概率。

2. **下单幂等，处理客户端重试与重复提交**  
   针对网络超时重试和重复点击可能造成重复创建订单的问题，引入会员维度的幂等键、请求摘要及数据库唯一约束；同一幂等键对应相同请求时返回原订单结果，对应不同请求时返回冲突，并以数据库唯一约束处理并发重复提交。

3. **条件状态迁移，解决支付与超时取消竞争**  
   针对支付回调与 RabbitMQ 延迟取消可能同时处理待支付订单的问题，将状态更新改为基于预期旧状态的条件更新，通过受影响行数确定状态迁移是否成功；只有成功完成“待支付 → 已支付”或“待支付 → 已取消”迁移的一方才能执行对应的库存确认或释放。结合支付回调幂等、支付状态查询及异常对账/退款补偿，处理支付已成功但订单已取消的异常场景。

4. **Outbox 可靠事件投递，弥合数据库与 MQ 的故障窗口**  
   针对订单数据库事务与 RabbitMQ 消息发送无法原子提交的问题，在创建订单的同一数据库事务中写入 Outbox 事件，由后台发布器扫描并重试投递，并通过 RabbitMQ Publisher Confirm 确认 Broker 接收结果；消费者按事件 ID 和业务唯一约束实现幂等处理，对超限失败事件进行告警并支持人工重放。
